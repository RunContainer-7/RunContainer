# Hosted companion relay — design

Status: **design + skeleton only.** Nothing here is deployed, and the Windows app does not
use it yet. The existing LAN and Tailscale paths keep working untouched.

## What it fixes

Today the PC is the server: the phone loads `http://192.168.x.x:7878/`, and the Home Screen
icon is bound to that address. Two consequences, both real:

- the icon dies when the router gives the PC a new address;
- an https page (our site) **cannot** talk to an http PC, so moving the page to a fixed
  origin does not move the *connection* with it.

The relay changes who is reachable. The phone opens a fixed `https://` page; the PC dials
out to the relay and keeps a socket open. Neither side needs a port, a router rule, an
account, or Tailscale.

```
 phone  ──https/ws──▶  relay (Worker, our domain)  ◀──wss outbound──  PC
        fixed origin                                   no inbound port
```

## The three parties

| Party | Knows | Never knows |
| --- | --- | --- |
| Phone | the site URL, a phone token, the PC's display name | the PC's address, the device key |
| PC | device ID, device key, the pairing code it shows | nothing about the phone beyond its name |
| Relay | device IDs, hashes of keys, room membership | app contents it does not forward, any plaintext secret |

## Identity

- **deviceId** — 128-bit random, generated on the PC on first run, stored beside the
  companion settings. Random, not a hardware fingerprint: it must not be derivable from the
  machine.
- **deviceKey** — 256-bit random, PC only. Sent once over TLS at registration; the relay
  keeps `sha256(deviceKey)` and compares in constant time. This mirrors the phone-token model
  the LAN server already uses, so there is one idea to understand, not two.
- **phone token** — minted by the relay on a successful pairing, stored by the relay as a
  hash in `phones`, and revocable by the PC. 30-day expiry, sliding on use.
- **pairing code** — six digits, five-minute life, eight attempts, one use. Generated by the
  relay at the PC's request and displayed on the PC, exactly like today's code.

## Flow

1. **Register (once).** PC → `POST /api/device` `{deviceId, deviceName, deviceKey}`. The relay
   stores the hash. Idempotent: a second call with the same deviceId and key is a no-op, a
   second call with a different key is refused (409) so a squatter cannot take an ID.
2. **Start pairing.** PC → `POST /api/pair/start` (Bearer deviceKey). Relay creates a code row,
   returns `{code, expiresAt}`. The PC shows the code. Starting again invalidates the old code.
3. **Claim.** Phone → `POST /api/pair/claim` `{code, phoneName}`. Relay checks the code, the
   attempt budget and the per-IP rate limit, then creates a phone row and returns
   `{token, deviceId, deviceName}`. The phone stores the token; nothing else is needed to
   reopen later — the icon goes straight to the app list.
4. **Tickets.** Both sides → `POST /api/ticket` with their own credential. The relay returns a
   short-lived room ticket for room `device:<deviceId>` with role `pc` or `phone`.
5. **Relay.** The room forwards frames verbatim. The companion protocol is unchanged: `hello`,
   `apps`, `view.meta`, `view.state`, binary JPEG frames, `input`, `view.start`, `view.stop`,
   `view.quality`.

## What the relay must not become

- **Not a store of anything.** Frames are forwarded and dropped. No recording, no history, no
  logs of app names.
- **Not a way in.** A phone token only reaches one device and only while that device is
  connected. Revoking the phone kills the ticket at the next mint.
- **Not end-to-end encrypted, and it must say so.** The relay terminates TLS, so it can see
  frames in transit. That is a deliberate, stated trade for not needing Tailscale. Phase 4 is
  optional E2E: derive a key from the pairing code, seal frames in the app, leave the relay
  with ciphertext.

## Threat model

| Attack | Answer |
| --- | --- |
| Guessing a six-digit code | 8 attempts per code, 30 claims per hour per IP, five-minute window |
| Replaying a code | Single use; the row is consumed on a successful claim |
| A stranger claiming a shown code | They would have to see the PC's screen; the code is displayed only there |
| Stealing a phone token | Bound to one device, revocable, 30-day expiry, no reuse across devices |
| Squatting a device ID | IDs are 128-bit random; re-registration with a different key is refused |
| A malicious page on our origin | Cannot mint a ticket without a phone token; tickets are same-origin only |
| Relay operator (us) reading frames | Accepted in phase 1; removed by phase 4 E2E |

## Failure modes

- **Relay unreachable** — the phone says so and keeps its last snapshot; the PC shows the
  same and retries with backoff. The LAN address and the Tailscale address keep working, so
  the relay is never the only way in.
- **PC off** — the phone shows the last app list with each app marked *PC offline*, exactly
  as 0.11.1 does for the cached page.
- **Code expired** — the PC's card offers a new one; the phone's field says *expired* rather
  than *wrong*.
- **Phone revoked** — the next ticket request returns 401 and the phone goes back to the
  code screen, without losing the device name.

## What is needed before anything is deployed

1. **A Freebuff Sites project** (preview environment). No domain purchase, no DNS, no
   Cloudflare account, no credentials in this repository.
2. **Storage** — one D1 database for `devices`, `phones`, `pair_codes`, `pair_attempts`.
3. **Realtime** — the managed room binding, so the relay does not run sockets itself.
4. **Two secrets** set through Sites → Secrets, never in chat or in git: the ticket signing
   key and a pepper for code hashing.
5. **Sign in with Freebuff is not needed** — pairing is the identity. Adding accounts would
   contradict the point of the feature.

## Phases

1. **Skeleton (this change).** Schema, pure pairing/token logic, HTTP endpoints, tests that run
   without deploying. No sockets.
2. **PC client.** Outbound WebSocket, reconnect with backoff, ticketing, and the settings
   surface. Tested locally with `wrangler dev` and two simulated clients.
3. **Phone page.** The companion client served from the fixed origin, storing `deviceId` and
   token, pairing by code, installable. Tested against the local Worker.
4. **Optional E2E encryption**, plus bandwidth accounting so one phone cannot saturate a PC.
